## Принятая структура B2B-каталога

| Раздел | Состав |
| --- | --- |
| Компьютеры и ноутбуки | ПК, ноутбуки, моноблоки, неттопы, рабочие станции |
| Серверы и хранение данных | Серверы, СХД, NAS, серверные комплектующие |
| Сетевое оборудование | Коммутаторы, маршрутизаторы, точки доступа, адаптеры, СКС |
| Комплектующие | CPU, RAM, платы, накопители, видеокарты, корпуса, охлаждение, БП |
| Мониторы и периферия | Мониторы, крепления, ввод, веб-камеры, рабочие гарнитуры, док-станции, кабели |
| Печать и расходные материалы | Принтеры, МФУ, сканеры, тонеры, картриджи, запчасти; оборудование штрихкодирования отдельной подкатегорией |
| Электропитание | ИБП, соответствующие АКБ, фильтры, распределение питания |
| Программное обеспечение | ОС, офисные приложения, серверные лицензии, безопасность |

Профессиональные дисплеи, интерактивные панели и решения переговорных подходят B2B: первоначально подкатегории мониторов/периферии, отдельный раздел при развитии направления.

Исключаем целиком Home Appliances, Cleaning equipment, Garden Tools, Power tools, КЛИМАТИЧЕСКОЕ ОБОРУДОВАНИЕ, Entertainment, Pro Audio: 998 строк исходного файла. Дополнительные исключения определяются по типу товара. Обычные телевизоры, планшеты, смартфоны и мобильные аксессуары остаются только под запрос, без публичной категории. Смарт-часы, фитнес-браслеты, бытовые умные устройства и портативная акустика исключаются. Сумки для ноутбуков и рабочие аксессуары не исключать только из-за слова «сумка».

Исходные группы IT, CE, Audio & video, Mobile и Computer Peripherals смешанные. Например, IT содержит ИБП, ноутбуки и кресла, CE — проекторы и фены. Отбирать и распределять их целиком нельзя. Исходную категорию хранить отдельно от категории сайта; неизвестные группы отправлять на проверку.

Рабочее дерево хранится в `product_categories` и инициализируется из `config/catalog-taxonomy.json`. `config/storefront.php` остаётся резервным источником для окружений без заполненного дерева. Меню хедера показывает все активные разделы и подкатегории, включая пустые. Выдача и счётчики учитывают только опубликованные товары.

## Как импорт работает сейчас

- `app/Admin/CsvImport.php`: семь сопоставляемых полей, чтение CSV, UTF-8/Windows-1251.
- `app/Http/Controllers/Admin/ImportController.php`: CSV/TXT до 20 МБ, предпросмотр, сопоставление, запуск очереди и отчёт ошибок. Прямой импорт XLSX не реализован.
- `app/Jobs/ImportAdminProducts.php`: обычный CSV-процесс, поиск существующей позиции по sku + полному названию, новые товары создаются неактивными. Уже назначенная подкатегория не затирается исходной категорией прайса.
- `app/Admin/CatalogDraftImport.php` и `catalog:import-drafts`: проверенный staging JSON, сохранённые сопоставления, журнал всех строк, новые неактивные черновики. По умолчанию существующие товары сохраняются без изменений; с `--update-existing` обновляются только цена, валюта и три поля остатков.
- Старый Filament ProductImporter оставлен для совместимости с прежними заданиями.
- `/admin/catalog-prices`: самостоятельная загрузка XLSX, фоновый предпросмотр без сохранения изменений, применение после проверки, история и полный отчёт. Используется тот же `CatalogDraftImport`; инструкции и настройки обработчика — в `catalog-preview.md`.

Новый путь поддерживает промежуточную разметку, отдельные исходные остатки и загрузку черновиков. В XLSX-процессе после подтверждения полного снимка обнуляются остатки исчезнувших позиций, если последнее обновление наличия принадлежит этому источнику. Карточки сохраняются. CLI-импорт по-прежнему не обнуляет пропавшие позиции самостоятельно. Обычный CSV-путь сохраняет выбранную колонку наличия в availability.

## Целевой процесс — предложение

1. Прочитать XLSX/CSV в промежуточный набор, сохранив номер строки, дату, источник и идентификатор загрузки.
2. Проверить структуру, валюту, цены, ключи, дубли, полноту файла. Пустые служебные строки не считать товарами.
3. Нормализовать пробелы и бренды. PN хранить текстом, сохраняя значимые символы. Не менять оригинальные данные без сохранения исходника.
4. Применить правила: включить, исключить, проверить. Неизвестное не публиковать автоматически.
5. Показать изменения: новые, изменённые, пропавшие, отклонённые и спорные позиции. Порог аномальных изменений определить после нескольких реальных загрузок.
6. Применить проверенный снимок. Сохранять прежний каталог при неуспешной загрузке; не публиковать частичный результат как полный.
7. Запустить отдельные задания фотографий/характеристик для новых или изменившихся идентификаторов. Не скачивать всё каждый день.

### Идентификация и сохранение редакторской работы

Предпочтительный ключ — источник + стабильный код позиции поставщика. В основном 32-колоночном прайсе есть отдельный ID поставщика; прежний 9-колоночный формат такого ID не содержит. Временное сопоставление: нормализованный бренд + PN + признаки варианта поставки; неоднозначности требуют проверки. Нельзя считать PN уникальным или использовать изменяемое полное название как постоянный ключ. Формат поставки сейчас находится в названии.

Цены, остатки и исходные сведения поставщика отделить от редакторских заголовков, описаний, категорий, фото и SEO. Ежедневный импорт не должен стирать ручную работу или менять URL товара. Хранить last_seen_at и историю загрузок.

«Есть», «Свободно», «Транзит» хранить отдельно и уточнить их смысл у поставщика. Не суммировать без подтверждённого правила. `>50`, `0` и пустое значение различать; не преобразовывать `>50` в точное количество 50. Налоговые условия из текста не считать универсальным правилом всех позиций.

Пропавшие товары обрабатывать только после успешного полного снимка данного источника. Принято: после успешного полного прайса остаток отсутствующей позиции обнуляется сразу, карточка и её публикация сохраняются. На витрине доступен запрос поставки. Историю, фото и постоянные страницы не удалять автоматически.

## Критерии готовности ежедневного обновления

- Повтор одного файла не создаёт дубли.
- Изменение цены или рекламной приписки не создаёт новый товар.
- Разные поставки одного PN не объединяются.
- Неизвестная категория не появляется на витрине без решения.
- Ошибка/обрыв импорта не снимает действующий каталог с продажи.
- Фото, редакторские данные и URL сохраняются.
- Видны дата последнего успешного обновления и отчёт изменений.
- Поведение проверено на этом прайсе и последовательности нескольких ежедневных файлов, включая пропажу и возвращение позиции.

## Визуальные совпадения фотографий

В очереди фото совпадения — предупреждение, а не запрет ручного подтверждения. Блок «Есть совпадающие» открывает сравнение текущего изображения и найденных фото других товаров. Можно подтвердить текущее фото либо выбрать существующее. Выбор фиксируется в `selected_match` результата задания; публикация по-прежнему выполняется отдельно на шаге «Результат».

`CatalogPhotoSimilarity` сравнивает актуальные изображения заданий (кроме отклонённых и заменённых), а также сохранённые галереи из `photo-quality/review.json`. Источники с изменившимися названием, брендом или артикулом исключаются. Перцептивный отпечаток `phash-dct32-v1`: белая подложка для прозрачности, яркость 32×32, низкочастотный блок DCT 8×8, медиана без DC. Порог — не более 6 отличающихся битов; отношение пропорций изображений — не более 1,25. Побайтовые копии определяются отдельно. Это эвристика сходства изображения, не проверка модели товара.

Отпечатки кешируются по SHA-256 имени файла в приватном хранилище. Для прогрева существующих файлов: `php artisan catalog:photo-fingerprints`. Новые файлы индексируются при обращении к очереди. Пересчёт алгоритма требует смены `PhotoPerceptualHash::VERSION`.

API сравнения и выбора требует прав управления товарами. Перед выбором сервер заново проверяет присутствие совпадения, неизменность исходного задания и качество выбранного файла. Флаги `shared_across_models` и `perceptual_match` не блокируют подтверждение; `small`, `blank`, остальные ошибки качества и конфликт EAN продолжают блокировать его.


## План и отчёт по усилению обновления прайса — 10 ноября 2026

Область этой доработки: семь согласованных улучшений текущего импорта и история карточки. Работа выполнена в локальном checkout; публикация на production не выполнялась. Компоненты интерфейса используют существующие shadcn/ui Card, Tabs, Table, Badge, Button, Input, Checkbox и Dialog.

1. **История и свежесть.** Из карточки доступен экран «История и источники». Сохраняются создание, правки через модель Product, изменение цены/остатков импортом, привязка источника, исчезновение, возврат и назначение подтверждённых фото. Есть значения до/после, сотрудник или система, источник и загрузка. Предпросмотр полностью откатывает события. Повтор без изменений не засоряет историю. Отдельно фиксируются последнее появление строки и последняя успешная проверка её данных. После 48 часов показывается предупреждение; ручная правка не продлевает свежесть. Старые записи не получают вымышленные даты. На странице загрузки виден последний успешный файл по каждому поддерживаемому источнику.
2. **Защита файла.** При новой загрузке обязательна дата прайса, указанная сотрудником. Повтор применённого файла, известный старый файл, дата ранее последнего прайса и загрузка, созданная до более новой применённой, блокируются. Файл старше двух дней и исчезновение не менее 30% идентичностей требуют явной отметки после проверки предупреждений. Сравниваются именно позиции, а не только количество строк: замена половины ассортимента при прежнем размере файла тоже обнаруживается. Проверка повторяется в обработчике перед записью; подтверждение связано с конкретным состоянием. Пустой или повреждённый предыдущий снимок не считается надёжным основанием. Для прежних загрузок без даты показывается предупреждение. Дата из имени файла не угадывается: неизвестный старый файл с неверно введённой датой определить достоверно нельзя.
3. **Итог перед применением.** Сохранены существующие счётчики и фильтры. Добавлены исчезнувшие позиции, точное количество обнуляемых карточек и число опубликованных товаров, у которых изменится цена или наличие. Расчёт использует реальный импорт и обнуление внутри откатываемой транзакции. Новые карточки остаются черновиками.
4. **Спорные позиции.** Используется существующая очередь и сохранение решений по отдельной позиции. Новые решения дополнены отпечатком бренда, артикула, EAN и формата поставки. Если данные изменились, решение возвращается на проверку. Ошибки цены/остатка нельзя обойти простым решением «включать». Ранее сохранённые решения без отпечатка сохраняют прежнее поведение; связанные позиции дополнительно защищены проверкой исходных данных поставщика.
5. **Подмена под прежним ID.** Для основного прайса изменение ранее известного бренда, артикула или EAN задерживает строку. Карточка и прежние исходные сведения не перезаписываются. Изменение нашего редакторского названия не мешает штатному обновлению цены. Новый ID поставщика автоматически не объявляется прежним товаром.
6. **Происхождение.** Во вкладке источников показаны ID поставщика, даты проверки и файл; для полей с новой историей — источник последнего изменения. Выбор фото из другой карточки фиксируется при назначении изображения на шаге «Результат» со ссылкой на исходную карточку. Данные до внедрения не выдаются за восстановленную полную историю.
7. **Запрос поставки.** Для отсутствующего товара используется «Запросить поставку», форма содержит количество и объяснение, что возможность, стоимость и сроки уточнит менеджер. Заявка хранит ID товара, количество, снимок названия и артикула; название берётся сервером из опубликованной карточки. Менеджер видит количество и переход к карточке в существующем разделе заявок. Скрытые товары и некорректное количество отклоняются. Существующие уведомления сохранены; тесты используют подменённую почту.

### Границы и эксплуатация

- История начинается с внедрения. Старые журналы импорта остаются доступны отдельно. Изменения прямыми SQL-запросами вне поддерживаемых процессов автоматически не фиксируются.
- Автоматического отката цены и остатков нет. Для старых загрузок нужно обновить предпросмотр, чтобы получить новые счётчики.
- До добавления второго поставщика требуется отдельная доработка модели предложений: идентификатор поставщика отдельно от формата файла, собственные цена/остатки каждого предложения и выбор предложения для витрины. Текущие профили файлов ещё не являются полноценным справочником поставщиков.
- Миграции: `2026_11_10_150000_add_catalog_audit` и `2026_11_10_150100_add_decision_identity`. Они применены к локальной MySQL-базе `altech`; коммерческие данные ради проверки не изменялись.
- Перед выпуском: применить миграции, собрать клиент и SSR, перезапустить долгоживущие обработчики очереди. Существующие queued-загрузки без даты потребуют проверки предупреждения.

- Миграции проверены тестами на SQLite и применены на локальной MySQL. Проверка процесса применения, ошибочных данных и записей истории выполнена на тестовых данных. Полный коммерческий прайс в рабочую локальную базу ради проверки не применялся.


### Уточнение интерфейса истории — 10 ноября 2026

Экран переработан: в карточке товара кнопка «История изменений», данные источника вынесены в отдельный компактный блок самой карточки. История показывает ленту событий с краткими изменениями и раскрываемыми подробностями. Фильтры «Все / Цена и наличие / Содержание / Фото / Публикация» применяются ко всей истории на сервере, сохраняются при переходе по страницам. Пустая история не показывает пагинацию.

Категории отображаются названиями (текущими названиями справочника), публикация — словами, характеристики — списком. Фотографии из сохранённых событий показываются миниатюрами, если исходный файл ещё доступен; доступ проверяется по правам сотрудника и принадлежности события товару. Сырые JSON и пути файлов в интерфейсе не показываются. Неизвестная дата проверки имеет нейтральный статус; устаревшие данные — отдельное предупреждение. Последний файл источника явно отделён от даты проверки конкретной позиции. Старый экран «История и источники» и таблица происхождения полей заменены этой подачей.

Проверено: TypeScript; сборка клиента и SSR; 14 тестов, 133 проверки. В данной боковой беседе браузерный инструмент не предоставил доступных браузеров, поэтому визуальная проверка нового варианта не выполнена. Коммерческие данные не редактировались.


Уточнение источника в карточке: «Последнее обновление из прайса» теперь определяется по журналу изменений именно этого товара (создание, обновление цены/остатка, обнуление исчезнувшей позиции) и соответствующей завершённой загрузке. Более новый файл источника, не изменивший товар, не подставляется. Если подтверждённая связь с файлом отсутствует, показывается «Источник последнего обновления не зафиксирован». Дата последней проверки позиции остаётся отдельной: неизменившийся товар может быть проверен более свежим прайсом. Проверены 14 тестов, 114 утверждений, включая выбор файла при наличии более новой посторонней загрузки.


### Единая карточка с вкладками

Просмотр и редактирование существующего товара объединяют вкладки «Карточка», «Источник», «История». Основные поля и фотографии находятся в карточке; прайс, актуальность, исходная классификация и описание поставщика — в источнике; лента с фильтрами и пагинацией — в истории. Простое переключение вкладок сохраняет форму и выбранные файлы в памяти. Переход по фильтрам/страницам истории при несохранённых правках использует существующее предупреждение об уходе. Пагинация сохраняет вкладку истории и фильтр. Для нового, ещё не сохранённого товара доступна форма создания. Проверены 17 тестов, 422 утверждения; TypeScript и сборка клиента/SSR.
