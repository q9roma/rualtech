# Прототип Lunar: товар → корзина → заказ

Дата: 5 ноября 2026. Локальный прототип, не готовый production checkout.

## Проверка совместимости

| Компонент | Результат |
| --- | --- |
| Lunar core 1.5.0 | Стабильный выпуск, установлен и зафиксирован в composer.lock |
| PHP 8.2.12 из XAMPP | Несовместим с Lunar 1.5 (требуется ^8.3) |
| Lunar core 1.4 + Laravel 12 + PHP 8.2 | Composer dry-run выявил конфликт cartalyst/converter; обход platform checks не используется |
| PHP 8.4.27 | Отдельный официальный Windows runtime в .tools/php84; SHA256 проверен, XAMPP не заменён |
| Laravel 12.71 / Inertia 3 / React 19 | Сохранены; ядро Lunar не навязывает frontend |
| Filament 4.16 | Существующая админка сохранена. Lunar admin 1.5 требует Filament ^4.1, но в прототип не устанавливается |
| shadcn/ui | Сохраняются стандартные neutral/new-york компоненты |

Источники: [Lunar core 1.5](https://github.com/lunarphp/core/tree/1.5.0), [Lunar admin 1.5](https://github.com/lunarphp/admin/tree/1.5.0), [Windows PHP](https://windows.php.net/downloads/releases/releases.json). Требования дополнительно проверены `composer show --all` и реальным разрешением зависимостей.

Lunar регистрирует глобальный binding `{product}`. В AppServiceProvider он явно возвращён к существующему App\Models\Product, иначе старые URL карточек возвращали 404. Заказы используют отдельный параметр `{commerceOrder}`. Дублировать миграции activity_log нельзя: их уже поставляет Lunar.

## Границы прототипа

- Источник товаров — существующая таблица products. ProductBridge создаёт нативные Lunar Product/ProductVariant/Price при добавлении в корзину; связь хранится в commerce_product_links. Исходные товары не заменяются.
- SKU поставщиков могут повторяться, поэтому технический SKU Lunar — ALTECH-{id}. Исходный артикул сохраняется в meta строки заказа.
- В корзину можно положить активный товар с положительной ценой RUB. Остальные позиции доступны по существующей форме запроса. Количество 1–99, максимум 50 строк.
- Цена преобразуется в копейки через BCMath, берётся только с сервера и перепроверяется перед оформлением. Изменение цены/состава требует повторного просмотра корзины.
- Корзина гостевая, привязана к сессии. Чужие строки и заказы недоступны. Мутации сериализованы блокировкой сессии и транзакцией с блокировкой строки корзины.
- Заказ создаётся штатным Cart::createOrder() Lunar. Товары, артикулы и суммы сохраняются снимком. Повторная отправка ключа checkout возвращает тот же заказ.
- Только самовывоз после согласования, без онлайн-оплаты, писем покупателям и отправки в CRM. Заказ получает статус prototype-pending-confirmation; деньги не списываются.
- Налоги отдельно не выделяются, используется исходная прайсовая цена. Это техническая проверка цепочки, не утверждённый расчёт НДС. Остаток availability — строка, поэтому резервирования и обещания наличия нет.
- Доступ включён по умолчанию только в local через LUNAR_PROTOTYPE_ENABLED. В production выключен. При STOREFRONT_INERTIA=false торговые маршруты тоже закрыты.

## Локальный запуск

```powershell
powershell -ExecutionPolicy Bypass -File scripts/setup-php.ps1
.\composer-local.bat install
.\php-local.bat artisan migrate
.\php-local.bat artisan commerce:setup-prototype
npm.cmd ci
npm.cmd run build
.\dev-local.bat
```

MySQL запускается в XAMPP. Новые команды PHP выполняются через php-local.bat, Composer — через composer-local.bat; системный PHP 8.2 больше не подходит для этого checkout. .tools не входит в Git и релиз. На Linux используйте PHP 8.4 с bcmath, exif, intl, gd и стандартными Laravel extensions.

Маршруты: карточка `/product/{id}` → `/cart` → `/checkout` → `/orders/{id}`. Корзина и заказы не индексируются. Непривязанный заказ виден в гостевой сессии. Заказ с user_id доступен только вошедшему владельцу, в том числе с другого устройства.

## Проверка и следующие шаги

### Кабинет покупателя

- `/register` — имя, email, пароль от 12 символов с подтверждением; `/login` — вход; `/account` — заказы; POST `/logout` — выход. Интерфейс использует стандартные shadcn-компоненты. В навигации добавлена ссылка «Личный кабинет».
- Используется Laravel web guard и существующая users; права is_admin нельзя получить через регистрацию. Filament остаётся на `/admin/login`. Вход в кабинет не предоставляет доступ к админке. Выход завершает общую web-сессию, включая вход в Filament.
- После входа/регистрации идентификатор сессии обновляется; после выхода сессия инвалидируется и CSRF-токен обновляется. POST-запросы защищены CSRF, лимитами и блокировкой сессии. Кабинет и детали заказов возвращают private/no-store.
- Заказы вошедшего покупателя получают user_id при оформлении. Список выбирается только по текущему user_id (15 на страницу), детали повторно проверяют владельца. Черновики не показываются. Статусы актуальны при загрузке страницы, без realtime-подписки.
- Непривязанные заказы из серверного списка commerce.orders показываются отдельно. Кнопка «Это мой заказ — привязать» отправляет только ID; сервер проверяет сессию, затем в транзакции блокирует заказ и допускает только пустого или того же владельца. Привязка повторяема; перепривязка чужого заказа запрещена. Ни email, ни переданный клиентом user_id доказательством владения не считаются. После привязки старый гостевой доступ не действует.
- Если гостевая сессия потеряна, самостоятельной привязки старого заказа в этом этапе нет. Подтверждение email и восстановление пароля ещё не реализованы; до публичного запуска их нужно добавить. Профиль, организации, повтор заказа и уведомления также остаются в плане. Торговый прототип и кабинет выключены при отключённых commerce.enabled или storefront.inertia.
- Проверки: 39 тестов / 657 assertions на PHP 8.4/SQLite; TypeScript и client/SSR build успешны. Проверены аутентификация, ограничения попыток, сохранение гостевой сессии при регистрации, явная привязка, отказ чужому владельцу/совпавшему email, пагинация, статусы и оформление вошедшим покупателем. Новые миграции и зависимости не понадобились.
- В браузере на локальной MySQL создан синтетический покупатель (example.test), явно привязан ранее созданный тестовый заказ 00000001, выполнены выход и повторный вход. После новой сессии заказ отображается в кабинете с актуальным статусом; ошибок JavaScript нет. Тестовый покупатель не имеет прав администратора. Письма и внешние интеграции не вызывались.

### Админка заказов и доступ покупателя

В существующий Filament 4 добавлен раздел `/admin/orders`: список оформленных заказов, поиск по номеру, фамилии и email, фильтр статуса; карточка показывает снимок состава, цены, итог, контакты, организацию, адрес и комментарий покупателя. Черновики не отображаются. Lunar admin отдельно не устанавливался. Доступ разрешён только сотрудникам с `is_admin`; создание, удаление и произвольное редактирование сумм через этот ресурс отсутствуют.

Кнопка «Изменить статус» предлагает допустимые переходы тестового процесса: ожидает подтверждения → подтверждён → готов к выдаче → завершён. Из любого незавершённого состояния можно отменить заказ. Завершение и отмена окончательны. Каждый переход требует комментария и сохраняет автора, время, предыдущий и новый статус в activity_log (log_name=order-status), история видна в карточке. Транзакция, блокировка строки и проверка ожидаемого статуса отклоняют изменения из устаревшего окна. Переходы не создают оплату, резерв, возврат, письмо или отправку в CRM. Неизвестные/нетестовые статусы этим процессом не изменяются.

На странице покупателя `/orders/{id}` теперь отображается актуальный статус при открытии/обновлении страницы. Реализованы регистрация/вход и список «Мои заказы», доступ владельца с другого устройства и явная привязка гостевых заказов. Повтор заказа пока не реализован. Совпадение email само по себе не даёт право на старые заказы.

Исправлено сохранение email оформления: Lunar ожидает `contact_email`, а форма отправляет `email`; теперь есть явное преобразование. Ранее созданные записи с пустым email автоматически не дополняются.

После добавления админки: 33 теста / 556 assertions успешно на PHP 8.4/SQLite, включая HTTP страниц Filament и Livewire-действие смены статуса, состав, контакты, фильтр, историю, права и конфликт изменений. TypeScript и client/SSR build успешны. Авторизованный интерактивный браузерный прогон админки в этом этапе не выполнялся; новые пользователи и права в локальной базе не создавались. Миграции для этого этапа не требуются.

Полный набор: 28 тестов / 508 assertions прошли на PHP 8.4 и SQLite. Торговые тесты проверяют серверную цену, изменение цены перед оформлением, количество и доступность, изоляцию сессий, идемпотентность и неизменность снимка заказа. TypeScript и сборка клиента/SSR проходят; Composer audit не обнаружил известных уязвимостей. HTTP SSR ранее проверялся для девяти страниц витрины; для трёх новых торговых страниц здесь проверена сборка.

На локальной MySQL выполнены миграции и справочники, в браузере пройден путь товара 28 → корзина → изменение количества до 2 → оформление → заказ 00000001 на 9 200 RUB. Использованы вымышленные контакты, оплаты и уведомлений нет. До миграций создан локальный backup `storage/app/private/backups/before-lunar-20261105-102604.sql`; он исключён из Git. Восстановление этого backup не проверялось.

Windows launcher использует PHP 8.4 и `serve --no-reload`, чтобы сохранить системное окружение дочернего процесса. После изменения .env сервер нужно перезапустить. XAMPP продолжает обслуживать MySQL; его PHP не заменён. `deploy:check` блокирует выпуск при включённом экспериментальном checkout.

До production нужны согласованные правила НДС, наличия и резервирования, доставки, оплаты и возвратов; модель покупателя и организации; приёмка сотрудниками реализованной админки и утверждение production-статусов; интеграции и уведомления; нагрузочные/конкурентные проверки на целевом MySQL, приёмка CI и staging. Прототип не утверждает внедрение всей платформы Lunar.
